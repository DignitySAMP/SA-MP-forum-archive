Sparse arrays

Introduction
Time after time, I see users using 2D or 3D arrays for string storage - which takes up a LOT of memory. This tutorial will teach you how to limit your use on sparse arrays, as well as save memory in your script.

What is a sparse array?
A sparse array is a multidimensional array which often has most of it's data empty, but it still takes up lots of memory.

Consider this code:

pawn Code:
#define MAX_ITEMS (128)

new g_String[MAX_ITEMS][64];
This array alone is a total of 8,192 cells - which is 32,768 bytes (32 kilobytes). For example, if you are only using 10/128 items, you are using 2,560 bytes, but there's still 29,208 bytes being unused!

However, since we're using global variables, this memory isn't allocated in any way, but the memory is dumped in the assembly line, which makes the .amx size larger in size.

Stack and heap
I won't be going into full detail here, since it's explained in detail in the PAWN Implementers Guide.

The "stack/heap" is simply part of the abstract machine that runs PAWN scripts, which controls and manipulates allocated memory from local variables. Very often, people find themselves using so much heap space that they end up running out and resort to using a "#pragma" instruction - but this is bad pratice!

Consider this variable:

pawn Code:
main()
{
    new var;
}
That variable alone is 1 cell (4 bytes). Arrays are basically "many cells in one", so the bigger array, the more memory you're allocating on the stack.

Local variables
Local variables are simply variables created within other functions or statements. When a function is called, that memory is allocated and used accordingly. On the other hand, global variables are not counted on the stack or heap - but they affect .amx size due to the memory dumps in the assembly line.

Why shouldn't I use a sparse array?
Sparse arrays shouldn't be used because they add unnecessary memory usage to scripts, which take up the heap space (mentioned above). There are much more better ways to store string data.
  • Packed arrays

    Packed arrays store data in each byte, rather than each cell, saving you 4 times less the memory.

    Consider this code:

    pawn Code:
    #define MAX_ITEMS (128)

    new g_String[MAX_ITEMS][64 char];
    This will allocate 2,048 cells on the stack (8,192 bytes, which is a reduction 7 kilobytes!). This isn't as much as bad as regular arrays, but packed arrays were designed for a reason!

    The following methods are ways to manipulate "dynamic memory" in PAWN without touching the stack or heap, but they also allocate memory regardless:

  • Linked lists

    A linked list is a data structure which consists of several nodes, all which represent a special sequence. Each node is composed of a data and a reference to the next node in the sequence.

    There is a library by BigETI that allows the possibility of linked lists in PAWN (frankly, I can't think of anymore). You can find it here:

    https://forum.sa-mp.com/showthread.php?tid=451962

  • Data containers

    A data container allows dynamic memory to be allocated, without having to specify a size for them. This data uses an internal linked list system (as far as I know, correct me if I'm wrong) and it doesn't take up any memory on the stack or heap.

    Here's a plugin for data containers:

    https://forum.sa-mp.com/showthread.php?tid=238844

  • Memory access plugin

    This plugin also allows you to dynamically allocate memory during runtime. It was created by BigETI.

    https://forum.sa-mp.com/showthread.php?tid=451381

  • y_malloc

    There's also y_malloc from YSI, which allows dynamic memory allocation too. It was created by ******.

    https://forum.sa-mp.com/showthread.php?tid=58827

  • Per-player variables

    For example, if you have an array like this:

    pawn Code:
    new g_JailReason[MAX_PLAYERS][128];
    If MAX_PLAYERS is 500, then that's 64,000 cells allocated (256,000 bytes, that's 250 kilobytes) onto the stack! I've seen LOADS of people do this before, so I'm not surprised.

    This is where per-player variables come in! Per-player variables are slower than variables in PAWN, but in this case, you do need them!

  • GVar plugin

    Similar to the same scenario above, however you are not dealing with players. It is not really necessary to use the GVar plugin, but it's just added for the sake of completing this tutorial.

    https://forum.sa-mp.com/showthread.php?tid=151076
